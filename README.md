# user-activation

Reusable Rust library for binding an application user identity to a specific sealed installation and requiring explicit authorization before the application becomes usable.

This library is designed to be independent from the application using it. SST is the first intended consumer.

## Scope

`user-activation` answers one question:

> Is this named user authorized to use this specific installation?

It does **not** identify the physical storage device by itself. That is delegated to `disk-seal`.

It does **not** provide OWNER or RECOVERY elevation. That is delegated to `owner-recovery-key`.

## First-run flow

On the first execution of an extracted application:

1. The application verifies its `disk-seal` identity.
2. The user is asked for a username.
3. The application warns clearly that the username is permanent and cannot be changed after activation.
4. The user confirms the name.
5. The activation library collects:
   - immutable username;
   - creation date and time, including UTC offset;
   - `disk-seal` installation identifier;
   - public device/install fingerprint supplied by `disk-seal`;
   - application version;
   - a cryptographically random nonce.
6. An activation request is created.
7. The request is sent or exported to the authorization authority.
8. The authority explicitly approves or denies it.
9. Only an approved, cryptographically signed activation permits normal application use.

## Activation request identity

A request identifier is derived from the immutable request data, for example:

```text
request_id = SHA-256(
    username
  || created_at
  || installation_id
  || disk_fingerprint
  || nonce
)
```

The request hash is an identifier, **not** the authorization itself.

## Suggested request payload

```text
username
created_at
installation_id
disk_fingerprint
nonce
application_version
request_id
```

Example human-readable request:

```text
USER            : MARCO
CREATED         : 2026-10-24T15:18:42-03:00
INSTALLATION ID : SST-7A3F-91C2-6D44
APPLICATION     : SST 0.1.8-blue.1
REQUEST ID      : 91C2-6D44-A873-08BF
```

## Authorization

The approval authority returns a signed activation record. A normal installation must never contain the private key capable of issuing valid activations.

The consumer application embeds only the public verification key or keys.

Suggested activation record fields:

```text
license_id
request_id
username
installation_id
created_at
approved_at
access_level
status
signature
```

The signed record makes the username effectively immutable: modifying it invalidates the signature.

## States

Recommended activation states:

```text
UNREGISTERED
PENDING
ACTIVE
DENIED
REVOKED
```

A consumer application should not enter its normal usable state unless activation is `ACTIVE` and all signatures and installation bindings verify.

## Access levels

The initial SST integration uses at least:

```text
USER
OWNER
```

`user-activation` is responsible for representing authorization metadata, but OWNER elevation and OWNER/RECOVERY credential handling belong to `owner-recovery-key`.

For SST, ordinary users are expected to receive `USER` activation. OWNER sessions require the separate privileged protocol.

## Registry integration

An authorization authority may maintain a central registry so an administrative application can list authorized installations.

Suggested registry metadata:

```text
installation_id
username
access_level
created_at
approved_at
license_id
status
last_seen
application_version
```

This enables an administrative SST command to distinguish normal user shells from owner shells and show pending, active, denied, or revoked installations.

The registry must never store private signing material.

## API direction

The eventual Rust API should keep transport separate from cryptography and state management. Conceptually:

```rust
let request = user_activation::ActivationRequest::create(
    username,
    disk_seal_identity,
    application_version,
)?;

let activation = user_activation::ActivationRecord::load(path)?;
activation.verify(&authority_public_key, &disk_seal_identity)?;
```

Possible traits/modules:

```text
request
record
verification
registry
transport
storage
clock
crypto
```

## Security rules

1. Username becomes immutable once the activation request is confirmed.
2. Creation date/time is part of the request identity, but must not be treated as trusted time by itself.
3. Approval time should be generated by the authorization authority.
4. Hashes identify requests; signatures authorize them.
5. Normal client installations never contain the private authorization key.
6. Activation must be bound to the `disk-seal` installation identity.
7. Copying an activation record to another sealed installation must fail verification.
8. Revocation state must be representable independently from the signed identity.
9. OWNER/RECOVERY credentials are outside this library.
10. Physical-medium binding is outside this library and belongs to `disk-seal`.

## Relationship to the SST security model

```text
disk-seal
    -> Is this the authentic physical installation?

user-activation
    -> Is this immutable named user authorized for it?

owner-recovery-key
    -> May this particular session elevate to OWNER or recover OWNER access?
```

These layers are deliberately independent so compromising one does not automatically bypass the others.
